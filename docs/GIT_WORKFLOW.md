# Інструкція для команди: Робота з Git через Forks та Pull Requests

> **Практична робота №2:** Командна робота, бізнес-документ і архітектурна діаграма  
> **Мета:** Відпрацювати командний Git-flow через форки (Forks) та Pull Requests (PR) у головний репозиторій  

---

## 1. Розподіл ролей у команді

Згідно з вимогами практичної роботи, ролі між учасниками розподіляються таким чином:

| Учасник | Роль у проєкті | Зона відповідальності | Відповідні файли |
| :--- | :--- | :--- | :--- |
| **Учасник 1 (Team Lead)** | Тімлід / Репозиторій-мейнтенер | Ініціалізація структури `docs/`, налаштування репозиторію, рев'ю та злиття PR-ів. | Базова структура, `docs/README.md` |
| **Учасник 2** | Бізнес-аналітик / Технічний письменник | Складання бізнес-документа: опис системи, ролі користувачів, Use Cases, функціональні та нефункціональні вимоги, обмеження. | `docs/business_doc.md` |
| **Учасник 3** | Системний архітектор (Architect) | Створення архітектурної діаграми (Client → Backend → Database + Auth, Notifications, Payments, AI) та її текстовий опис. | `docs/architecture_diagram.png`, `docs/architecture_diagram.drawio` |
| **Учасник 4** | Проєктний менеджер (Project Manager / PM) | Розробка дорожньої карти проєкту (Roadmap) на 3–4 тижні з декомпозицією завдань, оцінкою та критеріями готовності (DoD). | `docs/roadmap.md` |

## 2. Покроковий Git-flow для команди

### Етап 1: Дії Тімліда (Ініціалізація головного репозиторію)

1. **Створення гілки `master` або `main` та структури директорій:**
   ```bash
   # Ініціалізація папки документації
   mkdir -p docs
   git add docs/
   git commit -m "chore: initialize docs directory structure"
   git push origin master
   ```
2. **Налаштування доступу:**
   - Переконатися, що головний репозиторій публічний (або колеги мають доступ на читання).
   - Захистити гілку `master` (налаштувати вивантаження коду лише через Pull Requests з обов'язковим рев'ю).

---

### Етап 2: Дії учасників команди (Форк та розробка у своїх репозиторіях)

Кожен учасник виконує наступні кроки для своєї частини завдання:

1. **Зробити Fork (у веб-інтерфейсі GitHub / GitLab):**
   - Перейти на сторінку головного репозиторію Тімліда.
   - Натиснути кнопку **«Fork»** у правому верхньому кутку, щоб створити власну копію репозиторію у своєму акаунті.

2. **Клонувати власний форк на локальний комп'ютер:**
   ```bash
   git clone https://github.com/<YOUR_USERNAME>/<REPO_NAME>.git
   cd <REPO_NAME>
   ```

3. **Підключити посилання на головний репозиторій (`upstream`):**
   ```bash
   git remote add upstream https://github.com/<TEAM_LEAD_USERNAME>/<REPO_NAME>.git
   git remote -v
   ```

4. **Створити тематичну гілку під своє завдання:**
   - Для учасника 2 (Business Doc):
     ```bash
     git checkout -b feature/business-doc
     ```
   - Для учасника 3 (Architecture Diagram):
     ```bash
     git checkout -b feature/architecture-diagram
     ```
   - Для учасника 4 (Roadmap):
     ```bash
     git checkout -b feature/project-roadmap
     ```

5. **Виконати роботу та зробити змістовні коміти:**
   ```bash
   # Додаємо створені/відредаговані файли
   git add docs/business_doc.md
   
   # Створюємо коміт за стандартом Conventional Commits
   git commit -m "docs: add comprehensive business documentation for FitSync AI"
   ```

6. **Опублікувати гілку у власному форку:**
   ```bash
   git push origin feature/business-doc
   ```

---

### Етап 3: Відкриття Pull Request (PR)

1. Відкрити сторінку свого форку на GitHub.
2. Натиснути кнопку **«Contribute» → «Open pull request»** (або «Compare & pull request»).
3. Перевірити напрямок злиття:
   - `base repository`: репозиторій Тімліда (`master`)
   - `head repository`: ваш форк (`feature/...`)
4. **Оформити опис Pull Request за шаблоном:**
   ```markdown
   ## Опис змін
   Додано бізнес-документ системи FitSync AI з описом ролей, 5 сценаріїв використання,
   функціональних та нефункціональних вимог, а також обмежень системи.

   ## Що було зроблено
   - Створено docs/business_doc.md
   - Описано ролі: Gymtimidated Novice, Active Trainee, Pro Subscriber, Admin
   - Описано сценарії: онбординг, Home-to-Gym Bridge Plan, адаптація під час сесії, RPE калібрування

   ## Перевірка
   - [x] Відповідає вимогам Практичної роботи №2
   - [x] Відсутні конфлікти з гілкою master
   ```
5. Призначити Тімліда або іншого учасника як **Reviewer**.

---

### Етап 4: Code Review та злиття (Merge)

1. **Проведення рецензування (Review):**
   - Рецензент переглядає вкладку `Files changed`.
   - Залишає коментарі або затверджує зміни кнопкою **«Approve»**.
   - У разі потреби правок виконавець додає коміти у ту саму гілку у своєму форку — PR оновить дані автоматично.

2. **Злиття в головний репозиторій:**
   - Після схвалення Тімлід або відповідальний учасник натискає **«Merge pull request»** (рекомендовано обрати *Squash and merge* або *Rebase and merge* для збереження чистоти історії).

3. **Синхронізація форків іншими учасниками:**
   Щоб отримати актуальні зміни, злиті іншими учасниками:
   ```bash
   git checkout master
   git pull upstream master
   git push origin master
   ```
